# ALEPH 방어전 학생 틀: 제출 묶음

이 폴더를 학생 프로젝트의 시작점으로 복사합니다. `npm run bundle`은 **마지막 Git 커밋**에서 단계 설정, 바뀐 파일, 판정 규칙을 읽고, 그때 실행한 공격 점검 결과를 더해 `artifacts/submission.json`을 만듭니다. 제출 JSON을 손으로 편집하지 않습니다.

첫 프로젝트는 보호 장치가 없는 가상 자료실에서 시작합니다. `data.json`은 실습용 기록 네 건이며, Vercel 배포 시 `npm run build`가 같은 바이트를 `public/data.json`으로 복사합니다. 저장소를 만든 뒤 Vercel에서 이 저장소를 가져오면 `/`에는 점령된 자료실, `/data.json`에는 공개된 가상 기록이 보여야 합니다. 실제 학생 자료는 넣지 마세요. 2단계부터는 공개 복사 스크립트와 정적 자료를 제거하고 보호된 자료 API를 구현해야 배포할 수 있습니다.

처음 받은 뒤 `npm ci`를 한 번 실행합니다. `src/verify-login.mjs`는 자료 API의 서버 코드에서만 불러옵니다. `createLoginVerifier({ config, supabaseSecretKey: process.env.SUPABASE_SECRET_KEY })`를 서버 시작 때 만들고, 요청의 `Authorization` 헤더를 반환된 함수에 넘깁니다. 결과가 `null`이면 자료 없이 401로 거부합니다. 결과의 `userId`만 소유자 확인에 사용하고 브라우저가 보낸 `userId`나 `role`은 쓰지 않습니다. 이 키는 기존 서버 함수의 `SUPABASE_SECRET_KEY`를 그대로 쓰며, 브라우저 코드·응답·로그에 넣지 않습니다.

1. 코딩 도구에게 이번 단계의 `src/attack-check.mjs`를 실제 학습용 자료실에 맞게 고치고 실행 결과만 반환하게 합니다. 1단계 예시는 공개 배포 주소에서 가상 메모 확인 표시가 보이는지 검사합니다. 이후 단계는 같은 파일의 점검을 바꿉니다.
2. `aleph.config.json`의 단계와 주소·허용 경로를 코딩 도구가 갱신합니다. `src/decider.mjs`의 `RULE_IDS`에는 실제 구현한 규칙 이름만 남깁니다.
3. 학생이 만든 GitHub HTTPS 저장소를 `origin`으로 연결하고 이번 변경을 Git에 저장합니다. `bundle-notes.json`에는 학생이 직접 `explanation`(이번에 한 일 세 줄)과 `blockedAt`(막힌 곳, 없으면 `null`)만 적습니다. 예: `{"explanation":"가상 메모 세 개를 만들고 공개 배포를 확인했습니다.","blockedAt":null}`. 이 파일은 Git에 올라가지 않습니다.
4. `npm run bundle`을 실행합니다. 첫 오류가 나오면 코딩 도구에 그 오류만 보여 주고 고칩니다. `artifacts/submission.json`의 요약만 확인합니다. 이 파일 역시 Git에 올라가지 않습니다.

`aleph.config.json`은 단계가 올라갈 때 같은 파일을 고칩니다. 배포 ZIP의 `judgeIssuer`에는 학교가 정한 `https://aleph-judge-production.up.railway.app/defense/judge`가 들어 있으며 학생은 이 값을 바꾸지 않습니다. 저장소 원본의 빈 값은 ZIP 제작 때만 채웁니다. 1단계에서는 `step`·GitHub 저장소의 `repoUrl`·실제 `publicAppUrl`·공개 가능한 가상 메모의 `sampleMarker`를 적습니다. `repoUrl`은 `origin`과 같은 저장소여야 합니다. 3단계 제작 2는 `identityProvider`의 `issuer`·대상·공개키 주소를 실제 인증 프로젝트의 공개 설정과 맞춥니다. `jwksUrl`은 공유 비밀 방식에서 공개키 목록이 비어 있어도 프로젝트의 공식 주소를 적습니다. 도우미는 학생 토큰을 Supabase 공식 `getClaims`로 확인합니다. 3단계 제작 3부터 실제 자료 API의 메서드·경로를 `allowedRoutes`에 `{ "service": "notes", "method": "GET", "pathPattern": "/notes/:id" }` 형태로 적습니다. 자료 API는 `POST`에 `{id,title,body}`(id는 요청자가 만든 UUID, 없으면 서버가 만들고 `{id}` 반환), 한 건 `GET`에 `{id,title,body}`, `PUT`에 `{title,body}`, `DELETE` 2xx/404 뒤 같은 ID `GET` 404, 목록 `GET`에 로그인 사용자 메모 배열을 사용합니다. 4단계에서 추가·수정·삭제 경로와 필드 이름을 다시 대조합니다. 5단계 제작 2는 **쿼리 문자열이 없는** 원본 자료 API의 HTTPS 경로를 `originalApiUrl`에 적습니다. 비밀번호와 서버 전용 키는 이 파일에 넣지 않습니다.

`judgeIssuer`는 운영 측이 시작 ZIP을 만들 때 심판 접수 서버의 확인된 주소로 채웁니다. 학생은 이 값을 수정하지 않습니다. 빈 값인 소스 폴더를 그대로 복사해 수업에 쓰지 마세요.

심판 토큰은 이 주소의 ES256 공개키, 자료실 호스트 대상값, 15분 유효 기간, 실행별 신원을 확인합니다. 학생 로그인 토큰은 별도로 Supabase가 서명을 확인하며 1~5단계에서 HS256도 사용할 수 있습니다. 6단계 엔진 등록에는 비대칭 공개키가 필요합니다. 심판 접수 서버는 제출 설정의 `judgeIssuer`가 운영 등록 주소와 같은지도 별도로 확인해야 합니다.

`npm run bundle`은 필요한 단계 설정이 빠지면 어느 제작 단계를 다시 볼지 알려 줍니다. 생성된 JSON은 아직 심판의 방어 판정이 아닙니다. 심판 접수에서는 제출한 원본 주소가 운영 측에 등록된 주소와 같은지도 별도로 확인합니다.

실제 학생 계정, 메모 본문, 비밀번호, 토큰, 기기 개인키는 제출 묶음에 넣지 않습니다. 이 틀은 제출 형식의 로컬 후보이며 운영 심판 접수·학생 PC 검증·수업 배포가 끝났다는 뜻은 아닙니다.

`src/decider.mjs`는 처음에 모든 요청을 거부합니다. 6단계부터 코딩 도구와 함께 이 함수에 기기 조건을 비롯한 규칙을 하나씩 넣습니다. 함수는 제공 엔진이 확인한 요청을 받고, 같은 요청 ID와 허용·거부·추가 확인 중 하나, 이유 코드와 규칙 이름을 돌려줍니다. 구현한 규칙 이름은 같은 파일의 `RULE_IDS`에 기록합니다.

6단계 첫 규칙을 만든 뒤 `npm run decider:test`로 등록 기기의 정상 요청과 미등록 기기의 가상 요청을 비교합니다. 7단계 규칙 이름 `step_up_required`를 추가하면 복합 이상 접속과 최근 본인 확인을 마친 접속도 함께 검사합니다. 기본 시작 틀은 모든 요청을 거부하므로 규칙을 만들기 전 이 명령이 실패하는 것이 정상입니다. 이 결과는 로컬 연습이며 반 엔진의 실제 기기 확인이나 심판 통과를 뜻하지 않습니다.

9단계에서는 `docs/DETECT_EVENTS.md`를 읽고 `src/detect.mjs`에 조회 폭주 규칙을 작성합니다. `npm run detect:test`는 정상 30건, 경계 120·121건, 폭주 200건, 서로 다른 사용자, 10분 밖의 조회를 비교합니다. 기본 시작 틀은 모든 사건을 관찰만 하므로 규칙 작성 전에는 일부 항목이 실패합니다. 실제 사건 전달과 접속 회수는 반 엔진 연결 뒤 따로 확인합니다.

판정 요청의 실제 항목과 응답 형식은 `docs/DECIDER_REQUEST.md`를 먼저 읽으세요. 브라우저에서 보낸 역할·위치·기기 승인 값을 판정 요청에 만들어 넣지 마세요. 6~12단계 안내 원고는 현재 시작 틀과 맞추는 중이며, 이 문서가 ZIP에 포함됐다는 사실만으로 학생 배포 준비가 끝난 것은 아닙니다.

7단계에서는 `npm run fixture:7` 한 줄로 정상 사건과 복합 이상 사건을 비교합니다. 이 명령은 엔진의 공개 입력 형식을 흉내 낸 로컬 연습이며 심판의 실제 공격 결과가 아닙니다.
